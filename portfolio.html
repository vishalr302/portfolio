Grant Intelligence Platform

An explainable decision-support tool that turns IRS nonprofit records into a ranked list of potential grant-funder prospects for EcoServants.

View GitHub repository ↗ Open project brief

Problem

Nonprofit development teams can search large IRS Business Master File datasets for potential funders, but the raw records need extensive cleaning and do not directly answer whether an organization is likely to make grants or align with a nonprofit’s mission. Manual screening is slow, and an unexplained ranking is hard for a researcher to trust.

My approach

I built a readable Python pipeline that validates the raw data, narrows it to likely grantmakers, classifies mission fit, compares organization text with EcoServants’ mission, and ranks the remaining prospects with transparent rules. I connected the pipeline to a Streamlit dashboard so a researcher can search, filter, inspect, visualize, and export the same ranked data.

The work described on my resume processed more than 100,000 foundation records across eight Northeastern states. The current code supports the full nine-state U.S. Census Northeast region.

What I implemented

  1. Data ingestion and validation. The ETL layer accepts one or more IRS BMF CSVs, normalizes uppercase headers and common aliases, strips non-numeric EIN characters, drops invalid identifiers, standardizes whitespace and organization names, converts full state names to abbreviations, normalizes values such as 3, 03, and 501(c)(3), validates NTEE codes, and constrains asset and income codes to valid values from 0 through 9.
  2. Deduplication and regional scope. Files are combined, duplicate EINs are resolved by keeping the newest available tax-period record, and results are limited to Connecticut, Maine, Massachusetts, New Hampshire, Rhode Island, Vermont, New Jersey, New York, and Pennsylvania.
  3. Likely-grantmaker screening. The code keeps 501(c)(3) organizations whose names contain grantmaker signals such as Foundation, Trust, Fund, Charitable, Endowment, or Community Foundation. Matched terms remain available for review.
  4. Mission classification. A keyword-counting classifier assigns Environment/Conservation, Youth/Education, Community Improvement, Public Benefit, or Other. It also stores the exact keywords behind the assigned category, making the result easy to audit and adjust.
  5. Text similarity. Organization name, mission description, and program text are combined for analysis. A scikit-learn TF-IDF matrix is fit across EcoServants’ mission and all prospect text, then cosine similarity is converted to a 0–100 score. The name keeps the step usable when longer descriptions are missing.
  6. Explainable ranking. The 100-point model combines funder type (25 points), mission category (20), Northeast geography (15), NTEE alignment (15), financial codes (10), and TF-IDF similarity (15). Scores of 70 or higher are High Priority, 45–69.9 are Medium, and lower scores are Low. Each record includes component scores and a plain-language reason for selection.
  7. Interactive dashboard. Streamlit provides multi-file upload, sample-data fallback, organization search, state/category/priority filters, a similarity threshold, five summary metrics, four Plotly charts, a ranked table, and CSV download. The charts and table all use the same active filter state.

Key capabilities

  • Turns large, inconsistent IRS files into a smaller review queue.
  • Shows why each prospect received its category, score, and priority.
  • Supports missing descriptive text without stopping the pipeline.
  • Lets researchers export exactly the filtered records they are viewing.
  • Keeps scoring weights and keyword dictionaries in straightforward Python structures for later revision.

Validation and limitations

The automated tests cover record cleaning and deduplication, missing required columns, understandable category output, similarity and ranking behavior, Plotly chart creation, and cached dashboard pipeline output.

A grantmaker-style name does not prove that an organization accepts applications. IRS data can be missing or outdated, TF-IDF measures shared vocabulary rather than deeper meaning, and the scoring weights reflect EcoServants’ research priorities. Every lead still needs website, guideline, and Form 990 review.

Technologies

Python, Pandas, scikit-learn, TF-IDF, cosine similarity, Streamlit, Plotly, pytest, and CSV data processing.

02 · Computer vision and video analysis · 2025

NFL Pre-Snap Penalty Detector

An explainable computer-vision prototype that analyzes broadcast football video and flags suspected false starts, offsides, delay of game, and too-many-men violations.

GitHub repository ↗ Open project brief

Repository note: this URL is configured in the local project but is not currently publicly accessible.

Problem

Pre-snap penalty review depends on multiple events that unfold over time: player movement, team alignment, the line of scrimmage, the estimated snap, and sometimes the play clock. Broadcast footage makes the problem harder because of moving cameras, partial occlusion, changing scale, inconsistent uniform colors, and field graphics that may not be reliable.

My approach

I treated the project as an explainable first-pass review system rather than an automatic referee. The pipeline detects people in each frame, links them into tracks, estimates team membership and field position, identifies the collective movement peak used as the snap, and evaluates explicit temporal rules. Every flag includes a reason, confidence, snap frame, line-of-scrimmage estimate, and relevant event details.

The project work included analyzing more than 50 broadcast clips and tracking as many as 22 players in a play.

What I implemented

  1. Frame-by-frame person detection. The player detector loads a pretrained YOLOv8 model and filters person detections at a 0.35 confidence threshold with a 640-pixel inference size. Video utilities expose frame count, dimensions, and FPS and stream frames without loading the entire clip at once.
  2. Lightweight player tracking. A proximity tracker matches detections to recent tracks using center-point Manhattan distance, ignores tracks unseen for more than three frames, stores each bounding-box history, and accumulates uniform-color votes over time. Movement is normalized by player height so the signal is less sensitive to scale.
  3. Team and offense estimation. The initial heuristic labels blue-dominant crops as home, red-dominant crops as away, and ambiguous crops as unknown. Near the snap, the code can infer the offense from the median team position relative to the line and direction of play. CLI options allow the user to supply the offense and direction when the heuristic is weak.
  4. Line-of-scrimmage estimation. OpenCV converts the frame to HSV and searches a defined blue range for the largest field-line contour. If the overlay is not found, the code falls back to the mean player position; a manual --los-x override is available for more reliable analysis.
  5. Snap estimation. For each frame, the pipeline calculates the median of player displacements normalized by bounding-box height and chooses the largest collective movement peak as the estimated snap. If track-based motion is unavailable, it falls back to the largest average grayscale frame difference.
  6. False-start rule. In the one-second window before the snap, an offensive track is flagged after two consecutive observations beyond a movement limit of the greater of five pixels or 25% of the player’s height.
  7. Offside rule. A defensive track must first be more than four pixels on its own side of the estimated line and then cross more than four pixels onto the offensive side before the snap.
  8. Delay-of-game and too-many-men rules. Optional Tesseract OCR reads a user-selected play-clock region after grayscale conversion, enlargement, and Otsu thresholding. Delay of game requires at least two pre-snap zero readings and a 0.2-second grace interval. Too many men is flagged when more than 11 active tracks are assigned to a team near the snap.
  9. Structured output and review controls. The CLI accepts the video, optional model path, offense team, play direction, line location, play-clock crop, and OCR path. The structured result exposes the main flag plus all rule results, estimated offense, snap frame, motion peak, line location, clock readings, and detections for every frame.

Key capabilities

  • Evaluates four separate pre-snap rule categories in one pipeline.
  • Preserves track IDs and event frames for inspection.
  • Allows manual overrides for the assumptions most likely to fail.
  • Uses normalized motion and temporal windows instead of one-frame guesses.
  • Can annotate player boxes, team labels, and the estimated line of scrimmage.

Validation and limitations

The tests cover line estimation, tracking continuity, each of the four penalty rules, play-clock text parsing, peak-motion snap selection, and video input properties.

The flags are experimental, not officiating decisions. Camera movement, occlusion, legal shifts, inaccurate color classification, scoreboard delay, and an uncertain line can cause errors. Delay-of-game analysis needs a tight clock crop and a local Tesseract installation. Evaluation footage must also be footage the user is authorized to analyze.

Technologies

Python, OpenCV, YOLOv8, Ultralytics, NumPy, Tesseract OCR, pytest, video processing, object tracking, HSV segmentation, and rule-based temporal analysis.

03 · Web data collection and research tooling · 2026

Northeast Wildfire Smoke Scraper

An evidence-aware Python pipeline that collects official wildfire-smoke pages and turns inconsistent reporting into a consistent research dataset.

View my GitHub profile ↗ Open project brief

Repository note: a project-specific public GitHub repository has not been added yet.

Problem

Evidence about smoke reaching the Northeast is spread across NOAA, NASA, EPA, emergency-management, government, and other official pages. Sources use different wording and often omit fields that a researcher wants, such as incident dates, acreage, border movement, AQI, PM2.5, health advisories, and community effects. The main risk is not only missing data, but accidentally turning uncertainty into an unsupported claim.

My approach

I built a standard-library-first scraper that keeps source selection explicit, converts each page into readable text, extracts a fixed 29-field record, filters for Northeast relevance, removes duplicates, and exports the results in three useful formats. Deterministic rules are the default. Optional AI can fill difficult fields, but the program still controls provenance and instructs the model to leave unsupported values blank.

The project work consolidated more than 25 sources and automated more than 30 wildfire-smoke records across the Northeastern United States and Canada.

What I implemented

  1. Configurable source registry. JSON seed files define each source URL and optional research hints for the incident name, origin, year, location, dates, area, affected communities, and secondary evidence. The loader validates that the configuration is a list, rejects entries without URLs, and also resolves local fixtures for offline testing.
  2. Responsible fetching and caching. Remote pages use a named user agent, a default 1.5-second delay between requests, and a 30-second timeout. Each URL receives a SHA-256 cache filename, cached pages avoid repeated downloads, and a refresh option allows deliberate updates. A failed source is recorded in an error summary while the remaining sources continue.
  3. Readable HTML extraction. A custom HTMLParser removes scripts, styles, navigation, and markup noise while preserving headings and article text for rules or optional AI analysis. The scraper itself requires only the Python standard library.
  4. Structured research model. A dataclass defines 29 output fields covering incident identity, year and dates, origin and location, area and impacts, smoke direction, affected states and communities, border status, AQI and PM2.5, health advisories, source URLs, source organization, researcher notes, researcher name, and verification date.
  5. Evidence-aware rule extraction. The parser recognizes nine Northeast states and regional references, Canadian provinces, years, acreage or hectares, written dates, directional smoke sentences, AQI values up to 500, PM2.5 measurements, air-quality categories, advisories, and official-source domains. It records the highest valid AQI found and derives the standard category thresholds.
  6. Missing-data safeguards. Unavailable values remain Not Reported; uncertain international-border movement remains Not Confirmed. The program only confirms Canadian smoke crossing when a Canadian origin and an affected Northeast place are both present. Research notes preserve a short evidence sentence and a reminder to review the row.
  7. Northeast filtering and deduplication. Records are retained when affected-state, poor-air-quality, or research-note text contains a Northeast state or regional term. Duplicate records are identified using incident name, year, and primary source URL.
  8. Optional AI enhancement. When enabled with an environment-provided API key, the OpenAI Responses API receives the current row, the allowed field names, and up to 24,000 characters of article text. The prompt requires JSON, uses Not Reported for absent evidence, and forbids guessing border movement. Source URLs, source organization, researcher name, and verification date are restored from program-controlled values after extraction.
  9. Multiple deliverables. The CLI exports the same records to CSV for analysis, JSON for programmatic reuse, and a standalone HTML table for quick review. An included local fixture supports a full offline demo without internet access or API cost.

Key capabilities

  • Standardizes inconsistent sources into the same 29-column schema.
  • Preserves primary and secondary URLs, organization, researcher, and verification date.
  • Runs locally in deterministic rules mode with no paid service.
  • Supports optional AI without giving it control of provenance fields.
  • Produces an error list instead of losing the entire run when one page fails.

Validation and limitations

The tests verify the full 29-column CSV schema and exported values, successful extraction from a NOAA-style cross-border smoke fixture, and the safeguard that a local fire with no cross-border evidence remains unconfirmed.

Long-range smoke reports often describe a regional complex instead of one named fire. Rules can miss unusual wording, source pages can change, and optional AI output still requires human review. The pipeline intentionally refuses to invent incident acreage, dates, AQI, damage, or border claims when the source does not support them.

Technologies

Python 3.10+, urllib, HTMLParser, dataclasses, regular expressions, SHA-256 caching, CSV, JSON, HTML export, unittest, and the optional OpenAI Responses API.
